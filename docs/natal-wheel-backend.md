# Бэкенд: данные для персональной интерактивной натальной карты

## Цель

После покупки пользователь видит персональную натальную карту, построенную по дате, времени и месту рождения. Круг оформлен в принятой стилистике Asteria «Мягкий рельеф»: объёмный сиренево-жемчужный обод, мягкие пластилиновые поверхности, сдержанные золотые акценты, рельефные нити между планетами.

Внешний вид общий для приложения, а положения планет, связи и границы домов зависят от расчёта конкретного пользователя. Сервер возвращает числовые данные и существующие тексты разбора. Flutter размещает элементы, рисует круг и выполняет анимацию. Генерация PNG/SVG/видео на сервере для этой задачи не нужна.

## Что уже сделано в приложении

1. Вместо прежней декоративной иллюстрации подключён `NatalWheel`. Планеты размещаются по числовым долготам из `positions`; для Солнца, Луны и восьми планет предусмотрены отдельные символы.
2. При открытии мягко появляется обод и внутренняя часть круга, затем планеты и связи. Общая анимация появления занимает около 1,16 секунды. При включённом системном уменьшении движения карта показывается без этой анимации.
3. Связи между планетами рисуются объёмными нитями с рельефом и бликом. В текущей версии основные аспекты определяются на клиенте по разнице долгот.
4. Нажатие на планету выбирает её: выделяются сама планета и её связи, остальные элементы приглушаются. Под кругом появляется карточка именно этой планеты: название, знак, положение и имеющаяся интерпретация. Номер дома добавляется при точном времени рождения и корректных данных. Повторное нажатие снимает выбор. Выбор не делает новый расчёт, не вызывает генерацию текста и не расходует монеты.
5. Для ранее купленной карты предусмотрена отдельная догрузка геометрии через существующий расчётный метод. Она не вызывает покупку и не перегенерирует разбор. При ошибке сети сохранённые рабочие данные не стираются. Догрузка в этой реализации возвращает данные экрану и сама не записывает новый профиль.
6. В разделе с обзором есть уменьшенное превью той же персональной карты. Это не отдельная картинка с другим расчётом.
7. Клиент уже умеет читать, проверять и рисовать `house_cusps`. Без этого поля показывает доступные планеты и связи, но не придумывает границы домов.
8. При неизвестном/приблизительном времени рождения карта помечается как приблизительная; точные дома, ASC/MC и точные градусы в подписи планеты скрываются. Интерпретация в карточке выбранной планеты в этом режиме не показывается, остаётся доступное положение в знаке.

### Какие объекты сейчас интерактивны

`sun`, `moon`, `mercury`, `venus`, `mars`, `jupiter`, `saturn`, `uranus`, `neptune`, `pluto`.

Дополнительные объекты существующего ответа сохраняются. `ascendant` и `midheaven` используются как отметки ASC/MC при известном времени; они не входят в эти десять выбираемых планет.

### Аспекты текущей клиентской версии

| Аспект | Угол | Допуск |
| --- | ---: | ---: |
| Соединение | 0° | 6° |
| Секстиль | 60° | 4° |
| Квадрат | 90° | 5° |
| Трин | 120° | 6° |
| Оппозиция | 180° | 6° |

Это зафиксированные правила текущей визуализации. Для первой версии серверу достаточно вернуть корректные долготы; массив аспектов добавлять не требуется. Если серверный текст использует другие аспекты/орбисы, отдельно согласовать единые правила, чтобы текст и круг не противоречили друг другу. Не менять их скрыто только на одной стороне.

## Что известно о действующем API

Существующий метод:

`POST /api/v1/planets_houses_position`

Flutter отправляет `year`, `month`, `day`, `hour`, `minute`, `latitude`, `longitude`. Координаты — места рождения, а не текущей геолокации. Формат запроса в рамках минимальной доработки сохраняется.

Клиент читает существующие поля `data`, `elements`, `positions`, `house_summary`, `calculation`, `prompt_context`. В `positions` уже есть долготы объектов и номера домов, а в `calculation` — контекст времени, система домов и зодиак.

Предыдущая проверка действующего API 12 ноября 2026 года на искусственном примере (3 февраля 2001, 12:34, 51,5° / −0,12°) вернула 19 позиций, Placidus и Tropical. Массив точных границ домов отсутствовал. Это зафиксированная предыдущая проверка; повторный сетевой запрос при подготовке этой задачи не выполнялся. На бэкенде требуется подтвердить состояние актуальной версии.

## Обязательные изменения бэкенда

### 1. Добавить точные границы двенадцати домов

Добавить `house_cusps` на верхнем уровне существующего объекта результата расчёта, рядом с `positions` и `calculation`. Не заворачивать весь ответ в новую оболочку: текущий Flutter читает этот объект непосредственно.

При доступном расчёте поле содержит ровно 12 объектов:

- `house`: целое число 1–12; каждый номер встречается один раз;
- `longitude`: число, эклиптическая долгота начала дома, в градусах; `0 <= longitude < 360`;
- порядок: I, II, III, …, XII;
- значение `0` допустимо и не означает отсутствие данных;
- числа конечные, без `NaN`/`Infinity`, не строки и не подписи знаков;
- не округлять до целых градусов; сохранить точность расчётного движка;
- границы должны образовывать один последовательный обход круга через 0°.

Пример формы нового поля. Числа ниже условные, показывают валидный формат и переход через 0°. Они не являются эталонным результатом астрологического расчёта и не должны использоваться как данные пользователя:

```json
{
  "house_cusps": [
    {"house": 1, "longitude": 85.428608},
    {"house": 2, "longitude": 103.8},
    {"house": 3, "longitude": 127.2},
    {"house": 4, "longitude": 151.1},
    {"house": 5, "longitude": 184.5},
    {"house": 6, "longitude": 221.4},
    {"house": 7, "longitude": 265.428608},
    {"house": 8, "longitude": 283.8},
    {"house": 9, "longitude": 307.2},
    {"house": 10, "longitude": 331.1},
    {"house": 11, "longitude": 4.5},
    {"house": 12, "longitude": 41.4}
  ]
}
```

Это только фрагмент ответа. Все прежние поля сохраняются с прежним смыслом и типами.

Куспид — точка начала дома на круге. Существующее `positions[].house` отвечает на другой вопрос: в каком доме находится объект. Одного номера дома у планеты недостаточно, чтобы провести его границы.

### 2. Взять все координаты из одного расчёта

`positions`, `house_cusps`, ASC/MC и текстовый расчётный контекст должны относиться к одним и тем же исходным данным:

- дата и местное время рождения;
- широта/долгота места рождения;
- часовой пояс и его историческое смещение для момента рождения;
- один UTC-момент;
- одна система домов и один тип зодиака.

Использовать уже применяемый расчётный движок. Границы домов получать из его результата, без генерации языковой моделью и без подстановки 12 одинаковых секторов по 30°.

Сохранить `calculation.local_datetime`, `timezone`, `timezone_offset_hours`, `utc_datetime`, `house_system`, `zodiac`. Проверить, что они описывают тот же расчёт. Время и часовой пояс устройства не должны менять сохранённую карту рождения.

Для действующего Placidus проверить соответствие начала I дома ASC, начала X дома MC с учётом численной точности движка. Положение объекта в `positions[].house` должно соответствовать тем же границам.

### 3. Корректно обработать недоступные границы

Если движок не может вычислить выбранную систему домов для переданных данных, вернуть `house_cusps: null` либо не включать поле. Сохранить доступные положения планет и существующие данные расчёта.

Не возвращать частичный массив, дубликаты домов или нулевые значения вместо отсутствующих координат. Не переключать систему домов молча: альтернативный расчёт потребует явно отражённой системы и согласования поведения клиента.

Текущий Flutter принимает отсутствие поля и `null`, но не рисует дома. Ошибка только этой части расчёта не должна стирать уже купленную интерпретацию или превращаться в предложение повторно оплатить карту.

### 4. Проверить сохранение в профиле

При существующей записи и последующем чтении `planets_houses_data` новое вложенное поле должно сохраняться без потерь:

`planets_houses_data.house_cusps`

Если профиль хранит расчёт как произвольный JSON, новая колонка может не понадобиться. Достаточно проверить сериализацию, фильтры разрешённых полей, запись/чтение и добавить тест. Если используется строгая схема, расширить её.

Не менять типы и не удалять прежние поля. Не обнулять купленную `natal_card` при дополнении геометрии. Сохранить дополнительные объекты текущего `positions`, даже если Flutter не делает их интерактивными.

Для старых карт обязательна возможность повторно получить дополненный результат через действующий расчётный метод. Массовая миграция не требуется для начала работы: клиент умеет догружать координаты. Если требуется сохранять обновление старой геометрии между сессиями, сервер может сделать безопасное дополнение профиля по его сохранённым данным рождения; текущая клиентская догрузка сама PATCH профиля не делает. Выбранный способ описать в результате задачи.

### 5. Сохранять точность времени рождения

Клиент уже передаёт в данных профиля:

`personal_info.birth_date.birth_time_known`

- `true`: пользователь ввёл точное время, включая ровно `00:00` и `12:00`;
- `false`: время неизвестно либо указано приблизительно;
- отсутствие поля: старый профиль, точность нельзя объявлять подтверждённой только по подставленному часу.

Проверить запись и возврат этого флага без потери `false`. Не преобразовывать отсутствующее значение в `true`. Существующие исторические профили не переписывать массово с придуманной точностью.

В текущем запросе `planets_houses_position` этого флага нет: туда передаются числовые час и минута. По `00:00` нельзя определить, ввёл ли человек точную полночь или приложение использовало техническое значение. Если серверному этапу генерации текста нужна точность, читать подтверждённый флаг профиля; изменение запроса расчёта согласовать отдельно с Flutter. Не делать новый флаг обязательным в старом запросе без обновления клиента.

При неизвестном времени не выдавать в текстах точные дома, ASC/MC и выводы, требующие точного времени. Положения, чувствительные к часу рождения, трактовать как приблизительные.

### 6. Сохранить покупку и повторное открытие

Текущий сценарий покупки и правила доступа сохраняются. Не добавлять оплату за границы домов, выбор планеты, анимацию или повторное открытие.

- После подтверждения существующей покупки клиент получает прежний разбор и доступные расчётные данные.
- Геометрия для ранее купленной карты может догружаться без новой покупки и генерации текста.
- Повтор запроса геометрии не меняет баланс и не создаёт вторую платную операцию.
- Дополнение ответа не должно сломать регистрацию и другие существующие вызовы расчётного метода.
- Сбой догрузки не отменяет уже выданный доступ; повтор не расходует монеты.

### 7. Проверить тексты выбранных планет

Клиент уже читает существующие тексты из:

`natal_card.interpretations[language].planet_interpretations[planet_code]`

Проверить, что используются те же коды `sun` … `pluto`, что в `positions`, и что тексты относятся к этому пользователю и этому расчёту. Для RU/EN сохранить действующий формат локализации.

Если текст говорит о знаке или доме планеты, они должны совпадать с координатами и номером дома в расчёте. Новая генерация при каждом нажатии не нужна: карточка берёт уже полученный текст. Если отдельной интерпретации нет, Flutter сможет показать положение без выдуманного описания; добавление отсутствующих текстов обозначить отдельно, не смешивать с обязательным полем геометрии.

## Критерии приёмки

1. Есть обезличенный успешный ответ действующего метода со всеми прежними полями и 12 реальными `house_cusps`. Все границы сверены с расчётным движком.
2. Проверены два разных набора данных рождения. При изменении времени/места клиент получает результат именно нового расчёта; повтор одинаковых входных данных воспроизводит те же координаты с установленной точностью.
3. Проверены переход через 0°, граница ровно 0°, корректные номера I–XII, отсутствие дубликатов/частичного массива, согласованность ASC/MC и номеров домов планет.
4. Есть тест недоступного расчёта домов: границ нет, доступные планеты сохранены. Нет молчаливой подмены системы и фиктивных равных секторов.
5. Запись/чтение профиля сохраняет `house_cusps` и `birth_time_known`. Отдельно проверены точная полночь с `true` и неизвестное время с `false`.
6. Новая покупка даёт доступ к персональному кругу. Нажатие на каждую доступную планету показывает именно её карточку и подсвечивает её связи; нажатия не создают платных/генерационных запросов.
7. Ранее купленная карта открывается с прежним разбором, получает недостающую геометрию; баланс до и после одинаковый. Описано, сохраняется ли дополненная геометрия на сервере или догружается повторно.
8. Ошибка сети и повтор загрузки не стирают старые данные и доступ. Старый ответ без `house_cusps` продолжает читаться.
9. В режиме неизвестного времени круг помечен приблизительным, точные дома/оси скрыты, тексты не утверждают их достоверность.
10. После закрытия/повторного входа и смены устройства используется расчёт соответствующего аккаунта, без смешивания данных пользователей.
